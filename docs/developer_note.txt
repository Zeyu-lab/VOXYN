# VOXYN Developer Diary

## 2026-04-29 — Initial Project Setup

Today I created the initial structure for VOXYN.

VOXYN is planned as a lightweight voice-based community platform inspired by Discord. The goal is not to build a full Discord clone, but to create a small, usable, full-stack prototype that demonstrates real web application development skills.

The project should eventually include:

- User authentication
- User profiles
- Community servers
- Voice rooms
- Text chat
- Mini games
- Premium / payment system
- Supabase database integration
- RESTful backend APIs
- Cloud deployment
- Clear documentation

## Current Tech Stack Plan

Frontend:

- Vue 3
- Vite
- JavaScript
- CSS / possible UI framework later

Backend:

- Node.js
- Express.js
- RESTful APIs

Database / Auth:

- Supabase

Payment:

- Stripe test mode first

Possible voice system:

- WebRTC / LiveKit later

## Important Development Notes

### 1. Do not overbuild too early

VOXYN should not try to become a complete Discord replacement at the beginning.

The first goal is to build a small but complete working prototype.

The core user flow should be:

User signs up → creates a server → creates a room → joins a room → uses chat / voice / mini game → upgrades with payment

A complete small project is better than a huge unfinished project.

### 2. Build in stages

The development order should be:

1. Basic frontend and backend setup
2. Frontend connects to backend health API
3. Supabase authentication
4. Database tables for users, servers, rooms, and messages
5. Dashboard page
6. Server and room creation
7. Text chat
8. Mini games
9. Voice room feature
10. Stripe payment system
11. Deployment and documentation

Voice and payment should not be started too early because they are more complex. The basic app structure should work first.

### 3. Keep the folder structure clean

The project should stay organized:

- `frontend/` for Vue frontend
- `backend/` for Express backend
- `docs/` for documentation
- `routes/` for backend API routes
- `controllers/` for backend logic
- `services/` for frontend API calls
- `pages/` for main frontend views
- `components/` for reusable UI components

Do not put everything into one file.

### 4. GitHub upload rules

Before uploading to GitHub, always check `.gitignore`.

The following files/folders should not be uploaded:

- `node_modules/`
- `.env`
- `.env.local`
- `dist/`
- `.DS_Store`

Environment variables should be stored in `.env`, but only `.env.example` should be uploaded.

### 5. Use Git commits as checkpoints

Each major step should have a clear commit message.

Examples:

git commit -m "Add backend API structure"
git commit -m "Add frontend page structure"

### 6. Keep it portfolio-focused

VOXYN should be designed as a portfolio project for full-stack developer roles.

The project should clearly demonstrate:

- Frontend development
- Backend development
- RESTful API design
- Database design
- Authentication
- Payment integration
- Real-time or interactive features
- GitHub workflow
- Documentation
- Deployment

Every feature should be useful for explaining full-stack ability in an interview.

### 7. Supabase should be introduced after the basic app works

Do not connect Supabase before the frontend and backend are stable.

First, make sure:

- Vue app runs
- Express backend runs
- Backend health API works
- Frontend can fetch backend data

Then add Supabase authentication and database.

### 8. Payment system should use test mode first

The payment system should be built with Stripe test mode first.

The goal is to show a complete payment flow:

User clicks upgrade → backend creates checkout session → user completes test payment → success page loads → user premium status updates

Do not use real payments during early development.

### 9. Voice system should be simplified

Do not build a custom Discord-level voice server from scratch.

The better plan is to use WebRTC or LiveKit later.

The goal is to make voice rooms usable, not to build a professional voice infrastructure from zero.

### 10. Documentation matters

The `docs/` folder should eventually include:

- `architecture.md`
- `api-documentation.md`
- `database-schema.md`
- `deployment.md`
- `sprint-log.md`

This will make the project look more professional and easier to explain.
